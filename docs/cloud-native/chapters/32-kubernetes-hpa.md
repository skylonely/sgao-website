# 1. HPA概述（★★★★★）

HPA：

> Horizontal Pod Autoscaler，水平Pod自动扩缩容。

核心目标：

> 根据业务负载或监控指标，自动调整工作负载的Pod副本数量。

例如：

``` text
正常流量

↓

3 Pods


流量增加

↓

HPA扩容

↓

8 Pods


流量下降

↓

HPA缩容

↓

3 Pods
```

"水平扩缩容"强调：

``` text
增加 / 减少 Pod 数量
```

而不是直接增加单个Pod的CPU或Memory。

------------------------------------------------------------------------

# 2. 为什么需要自动扩缩容

固定副本数量存在两个典型问题。

## 流量高峰

``` text
Replicas = 3

↓

请求突然增加

↓

Pod负载过高

↓

响应变慢甚至故障
```

## 流量低谷

``` text
Replicas = 20

↓

实际请求很少

↓

大量资源空闲

↓

资源浪费
```

HPA希望实现：

``` text
负载增加 → 自动扩容

负载降低 → 自动缩容
```

从而兼顾：

-   可用性；
-   性能；
-   资源利用率；
-   成本。

------------------------------------------------------------------------

# 3. HPA整体架构

典型链路：

``` text
Pod运行指标

↓

Metrics Server / Metrics API

↓

HPA Controller

↓

计算期望副本数

↓

修改目标工作负载副本规模

↓

Deployment / StatefulSet

↓

Pod数量变化
```

HPA本身通常不直接创建Pod。

它调整目标工作负载的副本规模，再由对应控制器完成Pod管理。

------------------------------------------------------------------------

# 4. HPA与Deployment的关系（★★★★★）

常见架构：

``` text
HPA

↓

Deployment

↓

ReplicaSet

↓

Pods
```

职责区别：

## HPA

负责：

``` text
应该运行多少个Pod？
```

## Deployment

负责：

``` text
如何维持指定数量的Pod？
```

因此：

> HPA负责计算副本数，Deployment负责实现副本状态。

# 5. HPA工作流程

典型流程：

``` text
用户流量增加

↓

Pod CPU / Memory / 自定义指标上升

↓

指标系统采集数据

↓

HPA Controller周期性获取指标

↓

计算期望副本数

↓

调整Scale目标

↓

Deployment创建或删除Pod
```

形成闭环：

``` text
监控

↓

分析

↓

决策

↓

扩缩容

↓

再次监控
```

# 6. Metrics Server与指标采集

Metrics Server通常用于提供：

-   CPU；
-   Memory；

等资源指标。

结构：

``` text
Node / Kubelet

↓

资源指标

↓

Metrics Server

↓

Metrics API

↓

HPA
```

注意：

> Metrics Server主要提供资源指标能力，它并不是完整的长期监控存储系统。

生产环境的长期监控、告警和历史趋势分析通常还会使用独立可观测性系统。

# 7. CPU指标自动扩缩容（★★★★★）

CPU是HPA最典型的扩缩容指标之一。

例如目标：

``` text
平均CPU利用率 = 60%
```

当前：

``` text
Pod A = 80%
Pod B = 75%
Pod C = 85%
```

整体明显高于目标时，HPA可能增加副本数量。

扩容后：

``` text
3 Pods

↓

5 Pods
```

请求被更多Pod分担。

------------------------------------------------------------------------

# 8. Memory指标自动扩缩容

HPA也可以根据Memory等资源指标进行伸缩。

例如：

``` text
目标Memory利用率 = 70%
```

如果工作负载长期超过目标：

``` text
Memory持续升高

↓

HPA计算

↓

增加Pod
```

但需要注意：

> 并不是所有内存增长都能通过增加Pod解决。

例如：

-   内存泄漏；
-   单Pod本地缓存持续增长；

此时单纯扩容可能无法解决根因。

------------------------------------------------------------------------

# 9. HPA与resources.requests的关系（★★★★★）

上一章学习：

``` yaml
resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
```

当HPA使用资源利用率类型指标时，requests非常重要。

可以理解为：

``` text
实际资源使用量

÷

requests

↓

资源利用率
```

例如：

``` text
CPU request = 500m

实际CPU = 300m
```

利用率约：

``` text
300 / 500 = 60%
```

因此：

> 如果基于CPU或Memory利用率进行HPA，合理配置requests是重要前提。

------------------------------------------------------------------------

# 10. HPA副本数计算逻辑（★★★★★）

可以使用一个核心思想理解：

``` text
期望副本数

≈

当前副本数 × 当前指标值 / 目标指标值
```

例如：

``` text
当前Pod = 4

当前平均CPU = 80%

目标CPU = 40%
```

粗略计算：

``` text
4 × 80 / 40

=

8
```

因此期望副本数约为：

``` text
8 Pods
```

实际HPA行为还会受到：

-   容忍范围；
-   缺失指标；
-   Pod状态；
-   扩缩容策略；
-   稳定窗口；

等因素影响。

# 11. minReplicas与maxReplicas

HPA通常需要定义副本上下限。

例如：

``` yaml
minReplicas: 2
maxReplicas: 10
```

含义：

``` text
最少运行2个Pod

最多扩容到10个Pod
```

作用：

## minReplicas

保证基础服务能力。

## maxReplicas

防止：

-   无限扩容；
-   资源耗尽；
-   成本失控。

# 12. HPA YAML配置

示例：

``` yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler

metadata:
  name: web-hpa

spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web

  minReplicas: 2
  maxReplicas: 10

  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60
```

核心配置：

``` text
scaleTargetRef

↓

扩缩容对象


minReplicas / maxReplicas

↓

副本范围


metrics

↓

扩缩容依据
```

# 13. 自定义指标与外部指标

除了CPU和Memory，HPA还可以基于其他指标。

例如：

## 自定义指标

``` text
每秒请求数

队列长度

任务数量
```

## 外部指标

例如来自集群外部或外部监控系统的业务指标。

典型场景：

``` text
消息队列积压增加

↓

HPA

↓

增加Consumer Pod

↓

提高消费能力
```

这比单纯CPU指标更贴近部分业务负载。

# 14. 扩容与缩容行为

扩容和缩容的目标并不完全相同。

## 扩容

目标：

> 尽快应对业务压力。

``` text
负载上升

↓

快速增加Pod
```

## 缩容

目标：

> 在释放资源的同时避免频繁波动。

``` text
负载下降

↓

观察一段时间

↓

逐步减少Pod
```

因此生产环境通常：

> 扩容可以相对积极，缩容应更加谨慎。

------------------------------------------------------------------------

# 15. 稳定窗口与抖动控制（★★★★★）

如果指标在阈值附近不断变化：

``` text
59%

↓

61%

↓

58%

↓

62%
```

如果立即扩缩容：

``` text
扩容

↓

缩容

↓

扩容

↓

缩容
```

就会产生：

> 扩缩容抖动。

HPA可以通过behavior等配置控制：

-   扩容速度；
-   缩容速度；
-   稳定窗口；
-   单次变化比例或数量。

示意：

``` yaml
behavior:
  scaleDown:
    stabilizationWindowSeconds: 300
```

核心思想：

> 不要因为短时间指标波动频繁改变副本数量。

------------------------------------------------------------------------

# 16. HPA、VPA与Cluster Autoscaler区别（★★★★★）

三者经常混淆。

  机制                 扩缩对象        核心目标
  -------------------- --------------- ----------------
  HPA                  Pod数量         水平扩缩容
  VPA                  单Pod资源配置   垂直资源调整
  Cluster Autoscaler   Node数量        集群节点扩缩容

可以记忆：

``` text
HPA

Pod变多 / 变少


VPA

Pod变大 / 变小


Cluster Autoscaler

Node变多 / 变少
```

三层弹性：

``` text
应用层

HPA / VPA

↓

Pod层

↓

Node层

Cluster Autoscaler
```

# 17. 微服务弹性伸缩案例

假设电商系统：

``` text
API Gateway

↓

Order Service

↓

Payment Service
```

大促期间：

``` text
订单请求增加

↓

Order Service CPU升高

↓

HPA检测

↓

```

``` text

↓

↓

```

# 18. HPA常见问题

## HPA为什么不扩容？

可能原因：

-   指标系统不可用；
-   requests未合理设置；
-   当前指标没有超过目标；
-   已达到maxReplicas；
-   HPA目标对象配置错误。

------------------------------------------------------------------------

## HPA扩容后为什么仍然很慢？

可能原因：

``` text
HPA决定扩容

↓

Pod创建

↓

镜像拉取

↓

Container启动

↓

Readiness Probe通过

↓

开始接收流量
```

因此自动扩容并不等于：

> 新容量瞬间可用。

------------------------------------------------------------------------

## 为什么频繁扩缩容？

常见原因：

-   指标波动大；
-   阈值设置不合理；
-   缩容策略过于激进；
-   缺少稳定窗口。

------------------------------------------------------------------------

# 19. HPA生产环境最佳实践

建议：

1.  为Pod合理设置requests；
2.  设置合理的minReplicas；
3.  设置maxReplicas防止无限扩容；
4.  根据业务选择CPU、Memory或业务指标；
5.  配置稳定窗口减少抖动；
6.  关注Pod启动时间；
7.  配置Readiness Probe；
8.  对核心服务预留基础副本；
9.  监控HPA扩缩容事件；
10. 结合Cluster Autoscaler考虑Node容量。

还要注意：

``` text
HPA扩Pod

≠

集群一定有足够Node资源
```

如果Node资源不足：

``` text
HPA增加副本

↓

新Pod Pending

↓

需要扩容Node或释放资源
```

# 20. 系统架构设计师考点

## 什么是HPA？

答：

> HPA是Kubernetes水平Pod自动扩缩容机制，根据资源指标或业务指标自动调整工作负载的Pod副本数量。

------------------------------------------------------------------------

## HPA和Deployment是什么关系？

答：

> HPA计算并调整目标工作负载的副本规模，Deployment负责维护对应数量的Pod。

------------------------------------------------------------------------

## HPA为什么需要requests？

答：

> 当HPA使用CPU或Memory利用率指标时，利用率通常以实际使用量相对于requests计算，因此合理配置requests是资源利用率型HPA的重要基础。

------------------------------------------------------------------------

## HPA和VPA区别？

答：

> HPA通过增加或减少Pod数量进行水平扩缩容，VPA主要通过调整单个Pod的资源请求进行垂直扩缩容。

------------------------------------------------------------------------

## HPA和Cluster Autoscaler区别？

答：

> HPA调整Pod数量，Cluster Autoscaler调整Node数量。

------------------------------------------------------------------------

## HPA如何避免频繁扩缩容？

答：

> 可以通过稳定窗口、扩缩容策略和合理阈值减少短期指标波动造成的扩缩容抖动。

# 22. 本节小结

HPA核心知识：

1.  HPA实现Pod水平自动扩缩容；
2.  HPA根据资源指标或业务指标计算期望副本数；
3.  HPA通常通过Scale目标调整Deployment等工作负载的副本规模；
4.  Metrics Server可以提供CPU和Memory资源指标；
5.  使用资源利用率型HPA时，requests配置非常重要；
6.  minReplicas和maxReplicas控制扩缩容范围；
7.  自定义指标可以让伸缩策略更加贴近业务；
8.  稳定窗口可以减少频繁扩缩容；
9.  HPA调整Pod数量，VPA调整Pod资源，Cluster Autoscaler调整Node数量；
10. 生产环境需要将HPA与资源管理、监控、健康检查和节点容量统一设计。
