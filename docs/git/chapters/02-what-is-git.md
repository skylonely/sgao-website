# 第二章：Git 到底是什么

> **一句话理解：**
>
> **Git
> 不是保存文件，而是记录每一次变化，并把这些变化组织成一条可以追溯的历史。**

---

阅读本章后，你将能够：

- 理解 Git 的本质
- 理解快照（Snapshot）模型
- 区分 Git 与传统版本控制
- 理解 Repository、Commit、History 的关系
- 为后续学习工作区、暂存区和对象模型做好准备

## 📖 故事引入

很多开发者认为：

> Git 就是一个可以执行 `git commit`、`git push` 的工具。

实际上，Git 真正保存的不是"文件"，而是**项目在某一时刻的完整状态**。

当你再次提交时，Git 会生成新的快照，并把它与历史连接起来。

---

## 🏛️ Git 的设计思想

传统版本控制更多关注：

> 「某个文件修改了哪些内容？」

Git 更关注：

> 「整个项目此刻是什么样子？」

因此，Git 的核心单位不是文件，而是 **Snapshot（快照）**。

---

## 📦 快照模型（Snapshot）

假设项目只有两个文件：

```text
README.md
App.vue
```

第一次提交：

```text
Commit A
├── README.md
└── App.vue
```

第二次提交，只修改 README：

```text
Commit B
├── README.md（新版本）
└── App.vue（复用）
```

Git 会复用没有变化的数据，而不是复制整个项目，因此既高效又可靠。

---

## Git 与传统版本控制

| 对比 | 传统版本控制 | Git |
| --- | --- | --- |
| 保存方式 | 文件差异 | 项目快照 |
| 是否依赖服务器 | 通常依赖 | 不依赖 |
| 离线提交 | ❌ | ✅ |
| 分支 | 成本高 | 成本低 |
| 历史恢复 | 一般 | 非常强 |

---

## 🧩 Repository 是什么？

Repository（仓库）可以理解为：

> 一个保存完整项目历史的数据库。

里面不仅有当前代码，还保存：

- Commit
- Branch
- Tag
- 作者
- 时间
- 修改历史

所以复制一个 Git 仓库，也意味着复制了完整历史。

---

## 🌍 真实开发案例

团队准备发布新版本。

开发过程中：

- 修复了 20 个 Bug
- 新增 8 个功能
- AI 重构了部分代码

上线后发现问题。

由于每一步都有 Commit：

```text
Commit
   ↓
定位问题
   ↓
回退
   ↓
重新发布
```

整个过程都有据可查。

---

## 🏢 企业实践

优秀团队通常要求：

- 每个功能至少一个 Commit
- Commit 信息描述"为什么"
- 发布版本打 Tag
- 每次上线都可以回滚

Git 的历史记录，就是排查问题的重要依据。

---

## ⚠️ 常见误区

❌ Git 会保存所有文件副本。

实际上，Git 会尽可能复用未变化的数据。

---

❌ Commit 等于备份。

Commit 更准确的理解是：

> 项目在某一时间点的历史快照。

---

## 🏆 Senior Tips

- 学 Git 时，多想"状态"而不是"文件"。
- Commit 越清晰，后期维护越容易。
- 历史是一项资产，而不是负担。
